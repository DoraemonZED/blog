## 1. 可重复构建

构建的目标是同一份源码和锁定输入产生可追踪产物。Maven 以生命周期和 POM 管理依赖，Gradle 提供更灵活的任务模型。团队应固定 Wrapper 版本、Java Toolchain、仓库源和插件版本，不依赖开发机全局安装。

多模块按照业务或可独立复用能力划分，保持依赖单向。父工程统一版本和质量规则，但不要让一个公共模块变成所有服务共享的无边界杂物箱。

## 2. 依赖管理

直接依赖与传递依赖都要可见。使用 BOM 协调版本，定期扫描已知漏洞和许可证；升级后运行完整测试。禁止使用动态版本和来源不明的仓库，发布产物应生成软件物料清单并保存构建来源。

## 3. 测试金字塔

- 单元测试：快速验证领域规则，数量最多。
- 组件测试：验证数据库、消息和缓存适配器。
- 契约测试：验证服务之间请求、响应与消息 schema。
- 端到端测试：覆盖少量关键用户路径。
- 性能与韧性测试：验证容量、超时、重试和故障恢复。

测试必须可重复、相互隔离，不依赖执行顺序。涉及数据库行为时使用与生产相同类型和主要版本的临时实例。Mock 用于控制边界，不应把整套系统都 Mock 后宣称集成正常。

## 4. CI/CD 流水线

一次标准提交可以经过：格式检查、编译、单元测试、静态分析、依赖扫描、组件测试、镜像构建、镜像扫描、签名、部署测试环境、冒烟测试和审批发布。

产物只构建一次并在环境间晋级，不能每个环境重新编译。发布记录关联源码提交、构建日志、镜像摘要、配置版本和数据库迁移。

## 5. Docker 与 Kubernetes

镜像使用精简且受维护的基础镜像，多阶段构建移除编译工具，以非 root 用户运行。不要把密钥写进 Dockerfile、构建参数或镜像层。

Kubernetes 中设置资源请求和限制，依据测量结果配置水平扩缩容。探针、滚动策略和优雅停机共同决定发布期间是否丢请求。配置错误应在启动时失败，而不是流量到达后才暴露。

## 6. 配置与密钥

普通配置可以版本化，密钥进入专门系统。每项配置应有负责人、默认值、校验规则、作用范围和变更记录。动态配置发布应支持灰度和回滚；读取失败时要明确使用缓存值、默认值还是拒绝启动。

## 7. 可观测性与 SLO

从用户视角定义服务级别目标，例如可用性和延迟，再由错误预算指导发布速度。指标采用 RED（请求率、错误、持续时间）或 USE（利用率、饱和度、错误）组织。

日志结构化并脱敏，Trace 跨线程、消息和远程调用传播。监控系统本身也需要容量、采样和保留策略，防止高基数标签造成成本失控。

## 8. 性能工程

性能优化流程是建立目标、构造真实负载、测量、定位、修改和回归。分别观察客户端、网关、应用、JVM、数据库和下游。平均值会掩盖尾延迟，应关注分位数和错误率。

容量测试还要包含冷启动、流量突增、长时间稳定性和依赖降速。任何性能结论都应保存环境、数据规模、参数和原始结果。

## 9. 安全开发

- 最小权限运行服务和流水线。
- Secret 不进入代码、日志和制品。
- 依赖、容器和基础设施配置持续扫描。
- 输入校验，输出编码，使用参数化 SQL。
- 管理接口和调试能力默认关闭或强认证。
- 建立漏洞响应、密钥轮换和审计流程。

## 交付检查表

- 新环境能否只凭仓库和受控配置完成构建？
- 测试失败是否能明确定位？
- 制品能否追溯到源码和依赖？
- 部署是否可暂停、回滚或向前修复？
- Schema 变更是否兼容滚动发布？
- 告警是否代表真实用户影响？
- 密钥是否从未进入构建日志和镜像层？
