## 1. 先判断是否需要微服务

微服务的收益是独立演进、隔离和按边界扩缩容，成本是网络失败、数据一致性、部署数量和运维复杂度。团队规模较小、领域边界不清时，模块化单体通常更稳妥。拆分应围绕业务能力和数据所有权，而不是按 Controller、Service、DAO 技术层切服务。

## 2. 服务通信与治理

同步 HTTP/gRPC 适合需要立即结果的调用；消息适合解耦、削峰和事件传播。所有远程调用都可能超时、失败或返回不确定结果，因此需要明确：

- 连接和请求超时。
- 有界重试与随机退避。
- 幂等键和去重。
- 并发限制和背压。
- 熔断、降级和隔离。

重试会放大流量，不能在网关、服务和客户端每层同时无条件重试。只有幂等操作或具备幂等键的写操作才适合自动重试。

## 3. 网关、发现和配置

API Gateway 负责统一入口、路由、认证、限流和协议适配，但不要把业务规则全部堆在网关。服务发现维护实例与健康状态；客户端或代理执行负载均衡。配置中心保存动态配置时要有权限、版本、审计和回滚，密钥仍应交给专门的秘密管理系统。

## 4. 一致性与分布式事务

CAP 描述网络分区存在时一致性与可用性的取舍，并不意味着系统日常只能二选一。先定义每项业务允许多长时间不一致，再选择方案。

常见模式：

- Outbox：业务数据和待发布事件在同一数据库事务提交，再异步投递。
- Saga：多个本地事务配合补偿动作完成长业务流程。
- TCC：显式 Try、Confirm、Cancel，控制强但侵入性高。
- 幂等消费：通过业务唯一键、状态机或去重记录抵抗重复消息。

“消息只消费一次”通常要转化成“消息可能重复，但业务结果只生效一次”。补偿操作也要幂等。

## 5. 分布式基础能力

分布式 ID 需要唯一性、趋势性、可用性和信息泄露之间的权衡。分布式锁必须有租约、持有者标识和安全释放；超时后原持有者继续运行可能产生并发写，需要 fencing token 或数据库版本检查。

缓存一致性通常以数据库为事实源，更新后删除缓存，并处理并发重建、热点键和失败重试。不要追求脱离业务需求的绝对实时一致。

## 6. 消息与 Kafka/RabbitMQ

生产者关注确认、批量和失败重试；Broker 关注复制和持久化；消费者关注分区并行、偏移提交、重复与毒消息。消息 schema 需要向后兼容，事件表达已经发生的事实，不能随意改变历史含义。

积压时先确定瓶颈在生产、Broker、消费逻辑还是下游数据库。盲目增加消费者可能压垮数据库。

## 7. 可观测性

日志回答发生了什么，指标回答系统整体是否健康，追踪回答一次请求经过了哪里。统一传播 trace context，在关键边界记录服务、操作、耗时、结果和业务关联 ID。

告警应围绕用户影响和服务目标，例如错误预算、延迟与成功率，而不是为每个 JVM 指标设置固定阈值。

## 8. Kubernetes 与发布

容器化服务应无状态或把状态交给明确的持久化系统。正确设置 requests/limits、就绪探针、优雅停机和 PodDisruptionBudget。滚动、蓝绿和金丝雀发布都必须配合数据库兼容变更和自动回滚指标。

## 架构检查表

- 每个服务是否拥有清晰业务边界和数据？
- 下游超时是否小于上游剩余预算？
- 写操作是否具备幂等语义？
- 消息重复、乱序、延迟和丢失分别如何处理？
- 缓存、配置中心或注册中心故障时怎样降级？
- 能否从 traceId 定位一次完整调用？
- 发布是否兼容旧版本实例和旧数据库结构？
