## 1. 从源码到运行

Java 源码经编译形成 class 字节码，类加载器完成加载、链接和初始化，解释器与即时编译器共同执行热点代码。JVM 性能问题通常不是某一个参数造成，而是代码分配模式、堆布局、GC、线程竞争和外部依赖共同作用。

类加载遵循委派机制以维持核心类型的一致性。应用服务器、插件系统和热部署框架可能建立多个类加载器；“类名相同却无法转换”往往是类加载器不同。

## 2. 运行时内存

- 堆：对象和数组的主要存储区域，由 GC 管理。
- 线程栈：每次方法调用形成栈帧，包含局部变量和执行状态。
- 元空间：类元数据，使用本地内存。
- 直接内存：NIO 等组件可在堆外分配，仍需设置监控边界。
- Code Cache：保存 JIT 编译后的代码。

`OutOfMemoryError` 不等于“堆一定太小”。它可能来自 Java 堆、元空间、直接内存、无法创建本地线程或 GC 开销异常。诊断必须先确认错误类型。

## 3. 垃圾回收

判断 GC 是否健康应同时观察吞吐量、暂停时间、分配速率、回收后占用和晋升情况。选择回收器前先明确服务目标：批处理偏吞吐，在线接口偏延迟，大堆服务还要关注最坏暂停。

调参顺序建议：

1. 排除内存泄漏和无界缓存。
2. 确认容器内存限制被 JVM 正确认识。
3. 采集一段完整业务周期的 GC 日志。
4. 再调整堆大小、回收器和暂停目标。
5. 使用相同流量回归验证。

## 4. JIT 与性能陷阱

热点方法会被优化编译，类型假设失效时可能去优化。短时间压测可能仍处于预热阶段。反射、分支、逃逸分析、内联和对象分配都会影响结果，但不要根据理论猜测生产瓶颈。

基准测试应使用 JMH，并避免常量折叠、死代码消除、测试数据不真实和把 GC 时间排除在外。

## 5. 生产诊断流程

### CPU 高

1. 用系统工具确认进程和线程 CPU。
2. 将本地线程 ID 与线程转储对应。
3. 连续采样，而不是只看一次快照。
4. 使用 JFR 或性能分析器定位热点。
5. 判断是计算、锁竞争、GC 还是忙轮询。

### 内存持续增长

1. 观察 GC 后基线是否上升。
2. 在安全时机生成堆转储。
3. 分析支配树、保留大小和 GC Roots。
4. 检查缓存、监听器、ThreadLocal、类加载器和未关闭资源。
5. 修复后用相同负载验证。

### 请求卡顿

连续获取线程转储。如果大量线程处于同一锁等待，分析锁持有者；如果都在网络或数据库调用，检查超时、连接池和下游延迟。线程数增加通常不能解决下游已经饱和的问题。

## 6. 常用工具

- `jcmd`：统一诊断入口，可查看 JVM、类、线程、堆和 JFR。
- `jstack`：线程转储。
- `jmap`：堆相关信息；生产环境谨慎使用高开销操作。
- JFR/JMC：低开销事件记录和分析。
- GC 日志：理解暂停、并发周期和堆变化。

## 7. 上线基线

- 明确容器内存、堆、直接内存和线程预算。
- 开启可轮转的 GC 日志和必要的 JFR 策略。
- 对 OOM 转储设置安全目录和磁盘告警。
- 监控进程存活、堆、GC、线程、类加载、CPU 和接口延迟。
- JVM 参数进入版本控制，不在生产临时口口相传。
