1. Spring Boot 解决什么问题

Spring Boot 通过约定、自动配置、Starter 和生产运维能力减少应用装配工作。它没有替代 Spring，而是在 Spring Framework 之上根据类路径、配置和已有 Bean 推断合理默认值。

自动配置通常带有条件：某个类存在、某项配置开启、用户尚未声明同类 Bean。排查“为什么创建了这个 Bean”时，应查看条件评估报告，而不是盲目排除配置。

2. Starter 与自动配置

Starter 聚合一组协调版本的依赖；自动配置提供默认 Bean。自定义 Starter 应把使用方 API、自动配置实现和配置属性边界分清，使用条件注解允许用户覆盖，并提供清晰的配置元数据。

不要在业务应用中大量依赖隐式扫描。关键基础设施如数据源、消息客户端和安全组件应能从配置和启动日志中清楚识别。

3. 配置管理

配置来自属性文件、环境变量、命令行和外部配置源，优先级必须明确。使用 @ConfigurationProperties 绑定一组有类型的配置，并在启动阶段校验。

密码和 Token 不进入 Git、镜像或普通日志。生产密钥由专门密钥系统注入，并有轮换能力。Profile 适合环境差异，但不要复制一整套配置导致各环境长期漂移。

4. 日志与错误处理

日志采用结构化字段记录时间、级别、服务、环境、traceId 和业务标识。不得记录完整认证头、Cookie、密码或敏感个人数据。高频路径控制日志量，错误只在最能处理或最接近边界的一层记录，避免同一异常重复打印。

HTTP 错误通过全局处理器形成稳定协议，内部异常保留 cause。启动失败应直接退出，不应以“部分配置成功”的未知状态提供流量。

5. Actuator 与健康检查

存活检查只回答进程是否需要重启；就绪检查回答是否可以接收流量。把短暂的下游故障放进存活检查会造成重启风暴。管理端点需要独立保护，只公开必要信息。

核心指标包括请求率、错误率、延迟分位数、JVM、线程池、连接池和外部依赖。指标标签要控制基数，不能把用户 ID 或原始 URL 放进标签。

6. 测试

优先使用普通单元测试覆盖领域逻辑；用 @WebMvcTest 等切片验证 Web 契约；用完整启动测试验证装配；需要数据库、Redis 或消息队列时使用隔离的真实依赖环境。测试配置应尽量接近生产，不要用行为差异很大的内存实现掩盖问题。

7. 打包与容器部署

构建结果应可复现，镜像固定基础镜像版本并以非 root 用户运行。容器必须定义资源请求、限制、优雅停机和探针。应用收到终止信号后先停止接收新流量，再等待在途请求和任务完成。

分层镜像可以提高缓存命中率。Native Image 能改善启动和内存，但会增加构建复杂度，并对反射、动态代理和资源加载提出额外要求，应基于部署目标选择。

8. 版本升级

升级前阅读迁移指南和依赖清单，先升级到当前小版本，再跨大版本。建立编译、单元、集成、契约和性能测试基线，检查废弃配置、Jakarta 命名空间、序列化变化和监控指标变化。

上线检查表

  • 配置是否有类型并在启动时校验？
  • 密钥是否与普通配置分离？
  • 管理端点是否受保护？
  • 就绪与存活检查是否职责分开？
  • 是否支持优雅停机？
  • 构建是否可复现并能回滚？
  • 关键依赖是否设置超时、连接池和指标？
