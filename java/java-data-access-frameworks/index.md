## 1. 先选择抽象层级

不同数据访问方案解决的问题不同：

| 方案 | 优势 | 适合场景 |
|---|---|---|
| JDBC | 控制精确、依赖少 | 基础组件、极少查询 |
| Spring JDBC | 减少资源管理样板 | SQL 明确的业务系统 |
| MyBatis | SQL 可控、映射灵活 | 复杂查询、已有数据库 |
| JPA/Hibernate | 领域映射、变更跟踪 | 聚合边界清晰的领域模型 |

不要因为团队熟悉某框架就强迫所有查询使用同一种方式。复杂报表可以使用 SQL/MyBatis，核心聚合可以使用 JPA，但事务边界和数据模型必须一致。

## 2. MyBatis

Mapper 接口定义用例，XML 或注解承载 SQL。复杂结果映射使用 `resultMap` 明确字段关系，避免自动映射因列名变化而悄悄出错。动态 SQL 中值使用参数绑定，表名、列名和排序方向必须来自白名单。

一级缓存与会话相关，二级缓存跨会话但会增加一致性复杂度。缓存不是默认性能开关；需要明确失效、事务和多实例行为。分页要确认插件最终生成的 SQL，并对排序字段建立索引。

## 3. JPA 与 Hibernate

实体在持久化上下文中会被跟踪，事务提交时脏检查产生 SQL。理解实体状态、延迟加载、级联和 orphan removal，才能避免意外更新或删除。

N+1 查询是最常见问题之一。通过 fetch join、EntityGraph、批量抓取或专用 DTO 查询解决，但不能把所有关系都改成 eager。`equals/hashCode` 不应依赖会变化的字段，也要谨慎处理数据库生成 ID 在持久化前为空的情况。

## 4. 事务边界

事务通常放在应用服务层，覆盖一个完整业务用例。Repository 不应自行开启彼此隔离的小事务。只读事务是优化提示而不是安全权限；真正的只读控制还需要数据库账号和架构约束。

多数据源必须明确每个操作使用哪个数据源和事务管理器。本地事务不能原子提交两个独立数据库，必要时使用业务补偿、Outbox 或适合场景的分布式事务方案。

## 5. Redis、搜索与文档数据库

Redis 适合缓存、计数、短期状态和特定数据结构，不是把所有关系数据复制一份。缓存需要 TTL、容量、淘汰、穿透、击穿和一致性方案。

搜索引擎适合全文检索与聚合，不应默认成为交易事实来源。索引更新通常是异步的，接口必须接受短暂不一致。MongoDB 等文档数据库适合聚合以文档整体读写的场景，建模不能简单照搬关系表。

## 6. 多租户

常见方式包括共享表加租户列、同库不同 schema、独立数据库。隔离越强，成本越高。无论哪种方式，租户条件都应由基础设施自动注入并在数据库层建立约束，不能依赖开发者每次手写 where 条件。

## 7. 性能和测试

监控 SQL 数量、耗时、连接获取等待、事务时间和返回行数。开启 SQL 日志时必须参数脱敏。集成测试使用真实数据库版本验证方言、锁和事务行为；仅使用内存数据库无法覆盖生产差异。

## 检查表

- 框架选择是否符合查询和领域模型？
- 是否出现 N+1 或超大结果集？
- 动态 SQL 标识符是否有白名单？
- 事务是否位于完整业务用例边界？
- 缓存和搜索索引失效时系统是否仍正确？
- 多租户隔离是否有自动化测试？
